# Database Schema - Attendance Records

## Overview
Schema untuk fitur **Attendance Records** pada Fase 5 MVP.

**Deskripsi:** Sistem absensi berbasis RFID untuk siswa. Satu record = 1 kehadiran siswa pada 1 jadwal (schedule) di 1 tanggal.

**Dependencies:**
- `students` - dari Student Management (Fase 3)
- `schedules` - dari Schedule/Timetable Management (Fase 4)
- `users` - dari User Management (Fase 1)

## Indexes

- `PRIMARY KEY (id)`
- `UNIQUE INDEX (student_id, schedule_id, attendance_date)` - 1 siswa, 1 jadwal, 1 tanggal = 1 record
- `INDEX (student_id)` - Untuk query kehadiran per siswa
- `INDEX (schedule_id)` - Untuk query kehadiran per jadwal
- `INDEX (attendance_date)` - Untuk query kehadiran per tanggal/periode
- `INDEX (status)` - Untuk filter/report berdasarkan status kehadiran

## Enum: AttendanceStatus

| Value | Label (Indonesia) | Label (English) | Description |
|-------|-------------------|-----------------|-------------|
| present | Hadir | Present | Siswa hadir tepat waktu |
| late | Terlambat | Late | Siswa hadir tetapi terlambat |
| excused | Izin | Excused | Siswa tidak hadir dengan izin resmi |
| sick | Sakit | Sick | Siswa tidak hadir karena sakit |
| absent | Alpha | Absent | Siswa tidak hadir tanpa keterangan |

### Status Determination Logic

```
1. RFID Scan tepat waktu (sebelum/saat start_time) → status = present
2. RFID Scan terlambat (setelah start_time) → status = late
3. Input manual oleh admin/guru → status = excused/sick/absent
4. Tidak ada record sampai akhir hari → status = absent (generated by system/cron)
```

## Validation Rules (untuk Form Request)

| Field | Rules |
|-------|-------|
| student_id | required, exists:students,id |
| schedule_id | required, exists:schedules,id |
| attendance_date | required, date, before_or_equal:today |
| check_in_time | nullable, date_format:H:i:s |
| check_out_time | nullable, date_format:H:i:s, after:check_in_time |
| status | required, in:present,late,excused,sick,absent (atau menggunakan Enum validation) |
| rfid_scan_time | nullable, date |
| notes | nullable, string, max:500 |
| recorded_by | nullable, exists:users,id |

### Custom Validation Rules

1. **Unique Constraint:** Kombinasi (student_id + schedule_id + attendance_date) harus unik
2. **Date Validation:** `attendance_date` tidak boleh di masa depan
3. **Time Validation:** Jika `check_out_time` diisi, harus lebih besar dari `check_in_time`
4. **Status-Notes Validation:** Jika status = `excused` atau `sick`, field `notes` sebaiknya terisi (warning, bukan error)
5. **RFID Validation:** Jika menggunakan RFID scan, pastikan `rfid_card_number` dari siswa terdaftar dan aktif

---

## Business Rules

1. **One Record Per Schedule Per Day:** Satu siswa hanya bisa punya 1 record kehadiran untuk 1 jadwal di 1 tanggal
2. **RFID Auto-Detection:** Sistem menerima RFID card number, mencari student yang memiliki kartu tersebut, dan mencatat kehadiran
3. **Late Detection:** Jika waktu scan RFID > schedule.start_time, otomatis status = late
4. **Manual Override:** Admin/guru dapat mengubah status kehadiran secara manual (recorded_by akan terisi)
5. **Schedule Date Matching:** `attendance_date` harus sesuai dengan `day_of_week` pada jadwal (optional validation)

---

## RFID Scan Flow

```
1. Siswa tap kartu RFID di reader
2. Backend menerima: rfid_card_number + scan_time
3. Lookup student by rfid_card_number
4. Lookup active schedule berdasarkan:
   - student.classroom_id
   - current day_of_week
   - current time (between start_time and end_time, atau dalam tolerance window)
5. Determine status:
   - Jika scan_time <= schedule.start_time + tolerance → present
   - Jika scan_time > schedule.start_time + tolerance → late
6. Create/Update attendance record
7. Return response (success/error + student info + status)
```
